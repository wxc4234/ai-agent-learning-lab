# AI Agent 岗位面试作战手册：准备路线与 Codex 模拟面试

> 适用方向：AI Agent 前端工程师、AI Agent 应用开发工程师（偏前端）、Agent 产品工程师、AI Agent 全栈应用工程师<br>
> 项目依据：`chat-search/packages/chat-search` 与本仓库 `apps/`、`interview-questions/`<br>
> 制定时间：2026-09-07

## 0. 先说结论

面试准备不应该变成“把七个目录全部背完”。更适合当前经历的打法是：

1. 用 **ChatSearch** 证明自己处理过生产级 AI 产品中的流式协议、异步状态、一致性、性能、Hybrid 和大型前端工程问题。
2. 用 **AI Agent Learning Lab** 证明自己正在把前端优势扩展为 Agent Runtime、RAG、评测、可观测和 Python 后端的全栈交付能力。
3. 所有知识题最终都要回到项目证据：为什么这样选、失败过什么、怎样验证、还有什么边界。
4. 从现在起让 Codex 每周主持模拟面试。它一次只问一题，连续追问，不提前给提示，结束后再评分和纠错。
5. 不等全部准备完成再投递。达到本文的“首批投递门槛”后开始投递，用真实面试反馈调整后续训练。

一句话定位建议：

> 我过去主要做复杂 AI 搜索产品的前端工程，擅长把模型的流式输出、异步任务和不确定状态变成稳定、可恢复的用户体验；现在进一步补齐 Agent Runtime、RAG、评测与 Python 服务，目标是承担 AI Agent 产品从交互到服务端闭环的开发。

这条定位比“从前端转 AI、什么都重新学”更准确。前端经验是差异化资产，Python、RAG 和 Agent Runtime 是新增能力。

## 1. 两个项目在面试中的分工

| 项目 | 面试中证明什么 | 最适合回答的问题 |
|---|---|---|
| ChatSearch | 大规模真实业务、复杂异步链路、工程取舍、跨端和线上稳定性 | 项目深挖、前端架构、SSE、状态机、性能、故障处理、协作 |
| AI Agent Learning Lab | AI 全栈能力增长、端到端 Agent 产品、评测与可观测闭环 | Agent、RAG、Tool Calling、MCP、FastAPI、数据、系统设计 |

推荐叙事顺序：

```text
过去：在 ChatSearch 里解决生产级 AI 交互问题
  ↓
发现：AI 产品前端的核心不是聊天框，而是管理非确定性的运行过程
  ↓
现在：在 learning lab 中补齐 Agent Runtime、RAG、评测和后端
  ↓
目标：成为能独立交付 Agent 产品闭环的前端 / 全栈产品工程师
```

不要把两个项目讲成互不相关的经历。learning lab 应当是 ChatSearch 经验向 Agent 全栈自然延伸的证据。

### 1.1 事实边界

面试里必须区分以下三类内容：

- **我亲自负责**：可以用“我设计 / 我实现 / 我推动”，并准备代码、指标或复盘证据。
- **我参与协作**：说清自己的决策和交付边界，不把团队成果全部算到自己名下。
- **我从代码复盘或提出的改进**：明确说“当前实现是……，如果进一步增强，我会……”。

凡是不能确认的线上指标都不要编造。可以回答验证口径、埋点设计和希望查看的数据，但不能把计划中的改进说成已上线成果。

## 2. 准备优先级

### P0：必须形成稳定输出

#### A. 项目表达

- 30 秒个人定位。
- 1 分钟自我介绍。
- ChatSearch 30 秒、3 分钟、10 分钟三个版本。
- 两个可以深挖 3 层以上的 ChatSearch 难点。
- 一个失败或不完整方案，以及后续如何修正。
- learning lab 的目标、当前完成度、真实边界和下一阶段。

#### B. ChatSearch 核心题

先掌握下面六条主线，已有材料直接复用，不另背一套答案：

1. [项目总览与全链路](projects/chatsearch-overview.md)：从 HTML 壳、启动数据到回答进入 DOM。
2. [SSE 选型与流解析](projects/chatsearch-sse-vs-websocket.md)：Fetch SSE、字节边界、中断和恢复。
3. [双答案一致性](projects/chatsearch-ab-consistency.md)：稳定分支路由、完成屏障、幂等收口。
4. [Checkpoint 语义](projects/chatsearch-checkpoint-semantics.md)：best-effort 与严格不重不漏的差距。
5. [流式渲染背压](projects/chatsearch-render-backpressure.md)：网络完成不等于 DOM 完成。
6. [Hybrid](projects/chatsearch-hybrid.md) 与 [Vite/Rolldown](projects/chatsearch-vite-rolldown.md)：首屏、缓存、构建和依赖治理。

当前代码还可以形成一条新的深挖线：**task mode / 异步长任务**。准备时重点回答：

- 普通一轮回答与长任务在生命周期上有什么不同？
- 主 SSE、任务通知、详情续拉之间如何关联 `sessionId`、`qid` 和 checkpoint？
- 用户切换会话、页面离开、主动中止、网络断开时，哪些状态应保留，哪些资源必须释放？
- 迟到通知、重复注册、重复续拉如何做到幂等？
- 怎样构造本地连续流、截断流和恢复流来复现线上问题？
- 如果通知丢失或任务永久不结束，超时、轮询、补偿和最终状态怎样设计？

#### C. AI Agent 全栈核心题

- Agent UI 与普通聊天 UI 的区别。
- 如何把 token、plan、tool call、tool result、approval、error 映射成类型安全的前端状态。
- Tool Calling、ReAct、LangGraph、MCP 各自解决什么问题。
- Planning、Memory、Tool Use、Reflection 在代码中分别落在哪里。
- RAG 的 ingestion/query 两条链路，召回差时如何定位。
- 检索评测与 Agent 轨迹评测分别测什么。
- 如何回答“你怎么知道改动以后变好了”和“你怎么知道评测可信”。
- 超时、重试、幂等、权限、Prompt Injection、成本上限怎么处理。

### P1：保证不会明显失分

- JavaScript / TypeScript：事件循环、Promise、类型收窄、泛型、内存泄漏。
- 浏览器与网络：渲染流程、HTTP、缓存、跨域、安全、ReadableStream、AbortController。
- 前端工程：组件边界、状态管理、monorepo、构建拆包、性能指标、测试策略。
- 后端基础：FastAPI、asyncio、数据库事务与索引、Redis、鉴权与幂等。
- 系统设计：需求澄清、容量、数据流、失败路径、可观测、演进。
- 行为面试：所有故事保持同一条职业叙事。

### P2：控制投入

- 算法以常见 Medium 模式为主，重点训练边界、复杂度和口述过程。
- 模型训练、CUDA、复杂微调做到能解释定位和取舍，不投入大量实现时间。
- 不为了“框架数量”同时深挖多套 Agent 框架。

## 3. 把项目经历做成“证据卡”

每个准备讲的难点都填写一张卡。只写概念而没有证据，不算准备完成。

```markdown
## 主题

- 业务场景：什么用户动作或线上问题触发了它？
- 我的职责：我具体负责到哪一层？谁与我协作？
- 原始问题：可观察到的故障、性能问题或开发瓶颈是什么？
- 约束：兼容性、协议、时间、历史代码、跨端或团队边界是什么？
- 备选方案：至少两个，为什么没有选另一个？
- 最终行动：关键状态、数据流、异常路径和实现位置。
- 验证证据：测试、日志、指标、故障注入、线上反馈或代码位置。
- 结果：只写能确认的数据；没有数据就写验证方法。
- 当前边界：现在仍然不能保证什么？
- 下一步：如果多一周，会优先改什么？
```

ChatSearch 建议至少完成五张证据卡：

1. SSE 流解析与中断恢复。
2. 双答案状态机和完成屏障。
3. 网络生产速度与 DOM 消费速度之间的背压。
4. Hybrid BaseData、缓存和发问前 token 恢复。
5. task mode 长任务的通知、续拉、取消和资源清理。

从五张中选两张作为主故事。选择标准不是“代码最多”，而是自己参与最深、证据最完整、能讲清取舍。


## 5. Codex 模拟面试的正确分工

Codex 在面试准备中轮流承担四个角色：

| 角色 | 工作 | 不应该做什么 |
|---|---|---|
| 面试官 | 一次问一题、根据回答追问、控制时间 | 提前给答案或把问题拆成提示 |
| 评分员 | 按固定量表找证据、错误和表达问题 | 因答案流畅就默认技术正确 |
| 代码核验员 | 在允许的只读范围内核对实现和项目归属 | 把推断写成事实、修改业务仓库 |
| 教练 | 给改进答案和下一轮训练任务 | 一次安排十几个无法执行的改进项 |

严格模拟时，最好分成两个独立 Codex 任务：

- **面试任务**：只读取 JD 和指定代码，不读取已有标准答案；负责提问和记录原始回答。
- **复盘任务**：读取面试记录、代码和本题库；负责事实核验、评分和改进。

这样可以降低“面试官已经看过标准答案，于是不断暗示正确方向”的偏差。如果只用一个任务，也要明确要求：面试结束前禁止提示、纠错和展示参考答案。

官方 OpenAI 文档建议在提示中明确期望结果、行为边界、验证要求和输出风格；这正是下面提示词把角色、轮次、追问、评分和停止条件写清楚的原因。参考：[OpenAI Model guidance](https://developers.openai.com/api/docs/guides/latest-model)。

### 5.1 每次开始前提供的上下文

只给本轮需要的内容：

- 目标岗位或 JD；
- 面试轮次：项目面、基础面、系统设计、编码或 HR；
- 时长；
- 本轮允许读取的代码路径；
- 希望重点考察的 1～3 个主题；
- 是否允许看 `interview-questions/` 中的参考答案。

默认从 learning lab 项目启动 Codex，并把 ChatSearch 路径作为**只读项目证据**提供：

```text
/Users/wanxiancheng/chat-search/baidu/ps-se-fe-tpl/chat-search/packages/chat-search
```

涉及跨包链路时，允许继续只读 `packages/chat-sse`、`packages/chat-stream`、`packages/chat-huabu` 等相关包。模拟面试不需要修改 ChatSearch 代码。

## 6. 可直接复制的 Codex 提示词

### 6.1 45 分钟项目深挖面试

```text
你现在是招聘 AI Agent 前端 / 偏前端全栈工程师的高级面试官，请主持一场 45 分钟项目面试。

候选人的核心项目是 ChatSearch。只读代码路径：
/Users/wanxiancheng/chat-search/baidu/ps-se-fe-tpl/chat-search/packages/chat-search
必要时可以只读相关 workspace 包，但不要修改任何代码。

规则：
1. 一次只问一个问题，必须等我回答后再继续。
2. 从 30 秒项目介绍开始，根据我的实际回答连续追问 2～3 层，不按固定题单机械提问。
3. 重点考察我的职责边界、技术原理、方案取舍、失败路径、验证证据和当前限制。
4. 面试过程中不要提示答案、纠错、总结或展示评分。
5. 如果我使用了模糊词、虚构指标、把团队工作说成个人工作，继续追问证据。
6. 覆盖流式协议、异步状态一致性、渲染性能、长任务恢复或 Hybrid 中至少三个主题。
7. 时间到或我说“结束面试”后再进入复盘。

复盘时输出：
- 总分和六个维度分数；
- 最好的 3 个回答及原因；
- 风险最大的 3 个回答，区分事实错误、证据不足和表达问题；
- 每个问题给一个更好的口述结构，不替我虚构经历或指标；
- 下一次只安排 3 个最高优先级训练项。
```

```text
对我进行一场 30 分钟 ChatSearch 压力面试。把自己设定为熟悉浏览器网络、前端状态机和大型工程的 Staff 级面试官。
```

## 7. 固定评分标准

每次都使用同一套量表，分数才有可比性。

| 维度 | 权重 | 高分标准 |
|---|---:|---|
| 结构与表达 | 15 | 先结论后展开，2～3 分钟内讲清主线 |
| 职责与证据 | 20 | 个人边界明确，有代码、测试、日志或真实指标 |
| 技术正确性与深度 | 25 | 原理准确，能追到数据结构、状态和失败机制 |
| 选型与取舍 | 15 | 至少比较一个可行替代方案及其代价 |
| 异常、验证与边界 | 15 | 主动讲失败路径、验证方法和当前限制 |
| 岗位匹配度 | 10 | 能把经验映射到 Agent 产品和全栈交付 |

分数解释：

- **80～100**：可以稳定投递；继续修复具体薄弱项。
- **70～79**：可以开始首批投递，同时定向补缺。
- **60～69**：知识可能知道，但项目证据或表达还不稳定。
- **60 以下**：先修 P0 主线，不扩大题库范围。

单次分数会受题目影响。连续三次不同题目的完整模拟都达到 75 分以上，才说明表达开始稳定。

### 回答单题的口述结构

项目题使用：

```text
结论 → 场景与矛盾 → 我的方案 → 为什么这样选 → 验证与结果 → 边界
```

知识题使用：

```text
是什么 → 为什么需要 → 怎么使用 → 项目示例 → 取舍
```

系统设计使用：

```text
澄清需求 → 估算 → 主链路 → 数据与接口 → 失败路径 → 可观测与安全 → 演进
```
