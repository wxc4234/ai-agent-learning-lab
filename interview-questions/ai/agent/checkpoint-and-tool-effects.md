# Agent Checkpoint 为什么不能保证工具只执行一次？

> 优先级：P0｜参考答案已整理、尚未模拟｜工作后端 P1～P5 是源码理解，不代表个人实现；[版本与路径](../../projects/chatsearch-source-baseline.md)。

2026-10-23 恢复原分类题目；工作事实对齐 2026-10-22 已核验的业务提交 `77d5befe`，不是重新验收。本文保留 5 道通用知识题；具体工作链路、源码位置和失败边界统一见 [ChatSearch AI 全栈核对](../../projects/chatsearch-ai-fullstack-interview.md) Q2、Q8～Q13、Q20 与 K1/K2/K6。本文没有新增业务测试结果。

## 是什么与为什么需要

Agent Loop 在模型决策、工具执行和结果反馈之间循环；Checkpoint 保存可恢复状态，解决长流程暂停后接续。SSE 游标只描述事件传输位置，不能替代模型上下文、任务状态与工具执行记录。

## 1. ReAct、Tool Calling、MCP 和执行框架如何区分？

**参考答案：** ReAct 是围绕推理与行动反馈组织循环的方式；Tool Calling 提供模型提出结构化调用的接口；MCP 提供工具/资源接入协议；执行框架负责调度、上下文与生命周期。接入 MCP 不代表已经有完整 Agent，也不自动获得安全沙箱、权限、幂等或可靠恢复。

**项目反例：** P1 名称是 MCPPolling，但 list_tools 实际只注册 create。P2 的业务类 graph=None 并覆写 execute，P3 装配 ADK ReAct 与 middleware；不能只看 BaseAgent 或旧注释就说所有业务走同一默认图。

**追问与答案：** 工具参数符合 JSON Schema 就能执行吗？Schema 只解决形状/约束的一部分，执行层仍要核验主体、资源、允许操作和预算。工具输出和技能内容不是更高权限的指令来源。关联[技能契约](../../projects/chatsearch-skill-contract.md)。

## 2. 有 Checkpointer 就能任意时刻换机器恢复吗？

**参考答案：** 必须看持久化触发点和状态覆盖范围。P4 普通 put 只写内存，根命名空间的 interrupt 写入才持久化到 BOS；挂起后还可能发收尾事件，所以 repersist 刷新最终序号。P2 配置不可用时会退回 MemorySaver。这证明特定挂起恢复的设计，不证明每步都持久化或任意崩溃都可恢复。

**追问与答案：** 为什么不每个 token 都存？会增加延迟与存储成本，状态还可能巨大；可按业务恢复点和副作用边界存。要明确最大可丢进度、恢复时重复执行风险，以及持久化失败时是否允许继续。

**失败与验证：** 持久化前崩溃、BOS 写成功但回执丢失、恢复读超时、使用旧快照、配置导致内存回退。不能把外部读暂时失败缓存成永久不存在。

**核对边界：** 上述挂起持久化、收尾 repersist 和内存回退在旧版已经存在；不能描述成本次拉取新增。BOS key 存在也不能独自证明本次新快照覆盖成功；完整调用栈的异常分类与静态失败推演见统一核对 Q9，不作为已复现故障。

## 3. 传输恢复和执行恢复为什么必须分开？

**参考答案：** 浏览器从 Redis 重放只是补展示，不能重新跑工具。P5 的 open_for_resume 是执行侧恢复流，跳过已有首包并从保存序号后继续生产；它不是浏览器的 XREAD 游标逻辑。Agent 的状态、传输序号和历史消息需要关联，但不能共用一个字段就宣称原子一致。

**追问与答案：** 恢复到另一 worker 为什么危险？旧 worker 若仍执行，可能出现双写。需要执行租约、版本或 fencing token，并让副作用接收方拒绝旧代际；仅有分布式锁但下游不校验过期执行者，也可能继续写。此处是设计建议，不是对该快照已实现能力的断言。

**易错点：** 图状态恢复后还需重建 handler/writer 等运行对象；保存发送序号不等于所有事件已获 ACK，传输 ACK 也不等于浏览器已完成业务消费。控制面 claim 与租约的调用证据不能替代对底层原子领取、续租和下游去重的验证，见统一核对 Q10～Q12。

## 4. 工具成功、Checkpoint 未保存时怎么办？

**参考答案：** 直接重放会重复发邮件、创建任务或扣费。为写工具设计业务幂等键与持久调用记录，把未发出、执行中、已确认、失败和结果未知分开。回执丢失时先用业务键查外部结果；如果外部不支持幂等与查询，就保留未知并请求人工核对或业务补偿，不能假装提供 exactly-once。

**取舍：** 本地数据库原子事务只能覆盖本地状态；outbox 可保证待投递意图随业务提交，但外部消费仍要幂等。只读工具通常可更安全重试，但仍要复核权限、预算和数据时效。

**例子：** 外部建单成功，响应丢失，Agent 状态仍停在 tool_call。恢复时复用 operation_id 查询该单并写回 tool_result，而不是生成新键再建单。当前 P 的 Checkpointer 不足以单独证明这套副作用协议。

## 5. 如何评测 Agent，避免把“回答像成功”当成功？

**参考答案：** 以任务结果和工具轨迹双重验收：目标是否达到、权限是否越界、工具是否正确调用、失败是否保留未知、成本和延迟是否在预算内。模型文本说“完成”不证明文件/数据库变化正确；LLM 评分可辅助质量，确定性校验负责关键副作用与权限。

**失败集：** 重复 tool_call、同 ID 参数变化、超时后迟到成功、提示注入、权限中途撤销、循环超过预算、挂起后双 worker 恢复。报告成功率时分别保留失败、取消、未知与无答案分母。

**工作项目更新：** RSI 的版本化实验输入与环境还原属于评测准备能力，不能直接当作完整评分、自动晋升或线上收益；环境 replay 也不等于无副作用回放。具体实现与未验证边界见统一核对 Q20，通用评测方法仍以任务事实和失败分母为准。

**两个项目分别使用：** P 是工作项目后端源码复盘；Learning Lab 的[运行所有权](../../backend/web/agent-run-observability.md)与[检索评测](../evaluation/code-retrieval-metrics.md)是学习证据。不能把本地实验的召回率当作工作项目收益，也不能把工程测试通过等同独立掌握。
