# ChatSearch：从浏览器到 Go 网关与 Python Agent

> 优先级：P0｜来源：2026-10-22 本地源码复盘｜参考答案已整理、尚未模拟。
> 后端为协作理解，不自动计为个人实现。版本、路径与证据编号见[源码基线](chatsearch-source-baseline.md)。
> 本页保留 8 道跨服务项目题；Agent 执行、Checkpoint、工具调度的最新源码核对与失败边界统一见 [AI 全栈面试题与知识核对](chatsearch-ai-fullstack-interview.md)。以源码基线标注的固定提交为准，不把旧业务快照当作当前版本；本页不重复展开执行专题。

## 1. 一次任务请求为什么要拆接入、执行和事件回放？

**参考回答：** 浏览器连接的生命周期比长任务短。F 管理轮次与 UI，G 接受创建或恢复请求，把创建交给下游，并从 Redis Stream 向浏览器输送事件；P 的业务快照展示了后台 Agent 执行与向网关上报事件的独立链。这样浏览器重新订阅无需重新执行任务，但增加了事件保留、身份匹配、序号与跨服务故障处理成本。普通 conversation 另有 U 的执行图入口；Hoth 只是页面服务的一部分，不能当成模型执行后端。

**证据：** F3/F4、G1/G3、U1、P1/P2/P5。这些是不同本地版本的链路拼接，未做本轮联调。

**追问与答案：** 为什么不把所有逻辑放一个 HTTP handler？短任务可以简化部署；长任务若绑定连接，就会把断网、重试和执行副作用耦合。解耦后也不能直接承诺任务可靠落队，线程池 submit 不是持久队列。

**失败与验证：** 创建请求已被接受但响应丢失，客户端直接重试可能重复执行。建议引入请求意图键与状态查询，而不是靠 SSE 重连代替创建幂等；这是设计建议，未确认当前完整实现。

## 2. 为什么恢复第 11 条事件，Redis 的读取起点反而是 10？

**参考回答：** 当前前端把最大已接收序号加一写入 body checkpoint。网关把它解释为“包含第 11 条”，但 XREAD 读取严格大于起点的 ID，因此转换成 `10-0`。Header `Last-Event-ID` 本身表达上一条已收到的 ID，直接使用且优先于 body。若把 body 11 原样传给 XREAD，就从 12 开始，产生确定的边界丢包。

| 输入 | 网关起点 | 预期 |
| --- | --- | --- |
| body seq_id=11，无 Header | 10-0 | 从 11 起读 |
| Header=10-0，body=99 | 10-0 | Header 优先 |
| body=1 | 0-0 | 从首条有效事件起读 |
| 无新包又发生 reconnect | 保留上轮已接收最大值 | 避免回到开头 |

**证据：** F4、G2 的 resolveStartID 与 G5。已有测试代码可解释设计，但本轮未运行。

**追问与答案：** 这能保证不丢吗？只能修复起点换算，不能保证 UI 已提交、Redis 未裁剪、坏包可恢复。需要结合[Checkpoint 专题](chatsearch-checkpoint-semantics.md)和[Redis 语义题](../backend/distributed/redis-stream-delivery.md)。

## 3. 写 Redis 后才 ACK，为什么还不能说 exactly-once？

**参考回答：** G3 先 XADD，再 EXPIRE，再发送 ack_seq。写入失败不 ACK 是正确的顺序；但 Redis 已写、ACK 丢失时，上游仍可能重发。当前显式 `seq-0` ID 会拒绝重复或更小 ID，Handle 直接返回错误，并没有自动查旧 payload 后确认同一事实。唯一 ID 防止重复插入，不等于重复请求安全成功，更不等于工具副作用只发生一次。

**追问与答案：** 如何增强？用事件身份和内容摘要核对重复，确认相同再补 ACK，冲突则拒绝；业务写入用独立幂等键。还需明确 Redis 持久化、复制确认和故障切换策略，不能把注释中的“落盘”当成已验证配置。

**失败与验证：** 故障注入覆盖写入前失败、写入后 ACK 丢失、相同 ID 不同内容、TTL 过期、裁剪后旧游标。G3 默认 3 小时续期和近似最大 10000 条只是保留边界，不能承诺无限回放。

## 4. 浏览器变慢，背压会一路传到模型吗？

**参考回答：** 当前网关通过 io.Pipe 写 SSE，写阻塞会延迟本连接继续读取 Redis。Agent 却走独立上报链，仍可以持续 XADD；所以压力转移为 Redis 积压。前端组件 ack、网关流管道背压、模型生产节奏属于不同层，不能混说成端到端背压。

**证据：** G1/G2/G3；前端对照[渲染背压](chatsearch-render-backpressure.md)。

**追问与答案：** 如何估容量？按活跃任务数 × 每秒事件数 × 平均事件字节 × 保留秒数估原始数据，再加索引、对象、复制等开销；实际保留还受条数裁剪限制。关注最慢消费者落后量及恢复窗口，不只看平均吞吐。

**失败与验证：** 限速浏览器、快 Agent，观察内存、Redis 增长、裁剪、恢复缺口和连接清理。字节、事件大小、任务并发与保留时间都应有预算；目前不能从 maxLen 推断严格内存上限。

## 5. 切换会话、断网、停止任务是同一个取消操作吗？

**参考回答：** F3 明确把关闭全部后台 SSE 与中断任务分开。切换会话只停止本地订阅，后台任务继续；用户停止才走 interrupt。G 的 pump 使用 HTTP 请求 Context 控制订阅收尾；真正打断从 Redis 最新事件提取 AgentEndpoint，再转发到执行实例。转发成功也不自动证明模型、子进程和远程工具全部停止。

**追问与答案：** 执行实例重启怎么办？旧 Endpoint 可能失效。P 当前已经接入 Supervisor 控制面，native/legacy 还有不同的取消与恢复路径；不能把执行所有权和迁移机制一概说成尚未实现。跨服务仍需核对网关定位与持久任务归属、租约/代际、取消意图是否形成完整闭环，并以权威终态确认；不能靠无条件重发旧地址。具体执行边界见[最新核对专题](chatsearch-ai-fullstack-interview.md)。

**失败与验证：** 首包前点停止、切会话后迟到包、最新事件缺地址、重复停止、工具已提交但停止响应丢失。读原任务状态并保留未知结果，避免 UI 提前宣布副作用回滚。原理见[并发取消](../backend/concurrency/cancellation-and-resource-ownership.md)。

## 6. 首段回答结束、任务结束、用户看到完成如何区分？

**参考回答：** F4 的 taskProcess 只收口首段回答，辅助 SSE 继续接收任务执行包；G2 收到内部 DONE 后结束 pump，不把空 DONE 当正文。UI 还有自己的渲染完成屏障。三者不同，HTTP 200 也可能承载业务错误帧，因此分别记录接入成功、任务终态和可见完成。

**追问与答案：** 指标怎么设计？把请求接入、任务接受、首个模型事件、首个可见内容、任务终态、渲染完成分开计时。重连回放包含历史等待，不能混入实时首 Token 延迟。G2 对 query 路径不计算相同的实时写入延迟；缺时间点记 unknown，不补零。

**失败与验证：** 首段已出、后续工具失败；DONE 到达但组件卡住；HTTP 200 错误帧；回放旧事件。按任务关联日志，避免把 task ID 当无限基数指标标签。

## 7. 历史查询和删除如何体现真正的后端能力？

**参考回答：** U2 按 uid、session_id、message_id 查询，说明资源 ID 还必须绑定当前主体。U3 在同一个 Repeatable Read 事务中删除 topic 与 record，并使用同一个 QueryExecutor。它能保证这两次数据库写的提交边界，不能自动取消 Agent、删 Redis 流或阻止没有遵守同一协议的未来写入。

**追问与答案：** 加了事务就解决删除与生成并发吗？没有。需要确认写回答一方也检查会话状态或遵守锁/版本协议。可以设计删除标记、行锁、状态条件更新和 outbox；这是增强方案。DAO 上可变 DeleteInfo 是否安全还取决于实例生命周期，不能仅凭字段就宣布线上数据竞争。

**失败与验证：** 第二条删除 SQL 失败应整笔回滚；删除与追加竞争；重复删除；DB 已提交但 HTTP 丢回执。索引只能按查询提出候选 `(uid, session_id, message_id)`，没有 DDL/执行计划证据就不能说线上已有。见[事务与缓存](../backend/database/transactions-indexes-cache.md)。

## 8. AI 全栈系统设计面如何讲清服务演进？

**参考回答：** 先画接入、任务执行、事件存储、历史存储和浏览器五块，明确每个状态的权威来源。复用当前传输链时，先核对创建幂等、恢复窗口、现有执行所有权和观测机制的覆盖，再针对缺口补显式取消确认等能力；对外部写工具评估持久执行记录与查重。这里是演进建议，不代表当前没有 Supervisor 或执行观测。模型预算包括轮数、总时间、Token、工具并发和外部费用，不能只限 HTTP 连接时长。

**追问与答案：** 十倍流量先改哪里？先测活跃连接、XREAD 频次、事件体积、线程池排队和模型配额，再决定分片、合批或队列。把“加 Kafka / 多 Agent”当默认答案无法说明瓶颈。

**验证计划：** 正常闭环、断线恢复、慢消费、重复提交、服务重启、授权失效和工具未知结果都要覆盖；线上收益待真实指标，不能从源码规模推断。
