# Agent UI 的六态状态机如何设计？停止、错误和重试分别怎么处理？

> 主题：Agent UI / 状态机 / 错误恢复 | 频率：高 | 关联学习：`LEARNING_CURRICULUM.md` 第 3 周 Day 5

## 考点

- 是否能把流式请求拆成清晰的生命周期阶段。
- 是否能区分用户主动中止和系统失败。
- 是否考虑超时、断网、HTTP 错误、重试和重复消息。

## 核心答案（能直接讲出口的版本）

我会用六态状态机表示一次 Agent 请求：`idle`、`thinking`、`streaming`、`done`、`aborted` 和 `error`。状态不是为了增加复杂度，而是把每一种请求事件映射到唯一的 UI 行为，避免用多个布尔变量组合出互相矛盾的状态。

| 状态 | 进入条件 | UI 行为 | 允许的操作 |
|---|---|---|---|
| `idle` | 页面初始，或上一轮已经收口 | 等待提问 | 可以发送 |
| `thinking` | 请求已发出，但还没收到首个文本分块 | 显示“正在思考”，禁用重复发送 | 可以停止 |
| `streaming` | 收到首个文本分块，回答仍在持续 | 逐块追加回答，显示“正在生成” | 可以停止 |
| `done` | 流正常结束 | 显示完整回答，恢复输入 | 可以发送新问题 |
| `aborted` | 用户点击停止，或请求被主动取消 | 保留已生成片段，标记已停止 | 可以重新生成 |
| `error` | 超时、断网、500、502、429 等失败 | 显示可读错误和重试入口 | 可以重试 |

典型流转是：

```text
idle → thinking → streaming → done
             ├──────────────→ aborted
             └──────────────→ error

error/aborted → thinking（重试或重新生成）
```

`thinking` 和 `streaming` 必须分开：前者表示请求已经建立但还没有内容，后者表示用户已经看到部分回答。这样既能准确显示进度，也能正确决定停止时是否保留半截内容。

用户主动停止不能归为 `error`。停止是用户的正常控制行为，不代表服务故障；如果混成错误，UI 会错误地提示“请求失败”，监控数据也无法区分用户取消和系统异常。

错误提示要在前端统一转换，而不是把后端原始异常直接展示给用户。例如 429 显示“请求太频繁了，请稍后再试”，502 显示“模型服务暂时不可用，请稍后重试”，普通 5xx 显示“服务暂时出错，请稍后重试”，网络断开和超时分别提示检查网络或稍后重试。

重试应被视为同一轮请求的新尝试，而不是追加一条新回答。前端需要保存原问题和会话标识，重试前清空半截回答，再从空回答开始渲染；不能把新结果拼接到旧结果后面。更严格的“不重复保存”还需要服务端使用 `request_id`、`run_id` 或 Redis 幂等键，这属于后端幂等设计，不是前端状态机单独能保证的。

## 结合项目怎么讲

当前项目通过 Next.js BFF 发起流式请求，浏览器端使用 `AbortController` 负责停止。请求发出后先处于 `thinking`，读取到首个文本分块时进入 `streaming`，读取完成进入 `done`。用户点击停止时调用 `abort()`，进入 `aborted`；网络异常、超时或 BFF 返回 500/502/429 时进入 `error`，显示可读提示和重试按钮。

状态由一个 reducer 统一更新，而不是同时维护 `isStreaming`、`hasError`、`isAborted` 等多个布尔值。这样可以保证一次运行最终只进入一个终态：`done`、`aborted` 或 `error`。

## 简化记忆

- `thinking`：已发请求，还没内容。
- `streaming`：已有内容，仍在生成。
- `done`：正常完成。
- `aborted`：用户主动停止，保留半截内容。
- `error`：系统失败，给出可读提示和重试。
- 重试是“清空当前尝试后重新生成”，服务端幂等还要另行设计。

## 容易说错的地方

- 不要把 `aborted` 说成模型报错；它是用户控制产生的终态。
- 不要把“前端只显示一份回答”说成“后端一定不会重复落库”。
- 不要把 `thinking` 和 `streaming` 合并成一个模糊的 loading 状态。
- HTTP 状态码只能在响应尚未开始时表示错误；流开始后发生的错误必须通过流事件或客户端状态收口。
