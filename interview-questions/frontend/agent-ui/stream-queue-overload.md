# 服务端长期快于前端渲染时，如何限制队列增长并保证内容完整？

> 主题：Agent UI / 过载保护 | 频率：高 | 关联项目：[ChatSearch AI](../../projects/chatsearch-render-backpressure.md)

## 考点（面试官在考察什么）

- 流式状态、时序边界、异常收口与项目真实性。

## 核心答案（能直接讲出口的版本）

> 本题是扩展设计方案，不是项目当前已经落地的能力。

## **优化后的回答**

我会先把**完整内容存储**和**页面渲染任务**分开：内容按 `seq` 顺序保存，渲染队列只控制页面更新节奏。积压增加时，合并连续 Markdown、降低刷新频率，并关闭逐字动画、代码高亮和复杂卡片，优先保证文本可读。

队列需要同时限制任务数、内存和最长等待时间。接近上限时先批量持久化已解析数据；达到硬上限且服务端支持客户端主动 checkpoint 时，使用 `AbortController` 中断连接，优先追平本地积压，再断点续传，而不是让内存或落盘队列无限增长。

我会维护三个位置：`receivedSeq` 表示最后收到的包，`durableSeq` 表示已经连续落盘的位置，`renderedSeq` 表示已经完成渲染的位置。中断后更新 `generationId`，屏蔽旧连接的迟到回调；当积压降到阈值以下、主线程恢复稳定时，携带 `qid + durableSeq` 重连，由服务端从 `durableSeq + 1` 继续返回。

恢复后对小于等于 `durableSeq` 的包去重，并检查下一包是否连续；出现缺口则再次从缺失位置恢复。正常结束也必须等待结束包之前的内容全部保存并渲染完成，才能触发 `answer-end`。

如果服务端不支持可靠 checkpoint，只有在本地写入速度持续高于接收速度且空间充足时才继续落盘；否则进入明确的 client-overload 错误状态，不能为了稳定内存直接丢弃旧内容。

## 方案速记

`内容与渲染分离 → 合并与降级 → 达到硬上限后中断 → 追平积压 → checkpoint 续传。`

## 前提与边界

- 主动过载续传要求服务端支持客户端携带 checkpoint 重连。
- 暂停 `ReadableStream.read()` 不等于服务端一定停止生产。
- IndexedDB 只做有限缓冲，不能成为另一个无限队列。
- 这是扩展设计，不能表述成项目当前已经实现。
