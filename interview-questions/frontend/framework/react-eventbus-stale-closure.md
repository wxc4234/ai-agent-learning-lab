# React EventBus 订阅为什么会重复，并读取到旧的 `queryId`？

> 主题：框架 / React | 频率：高

## 考点（面试官在考察什么）

- 框架生命周期、状态闭包和组件正确性。

## 核心答案（能直接讲出口的版本）

旧 `queryId` 来自闭包保存了订阅建立时的值；重复订阅通常是 Effect 重新执行后没有正确清理，或者订阅与取消订阅使用了不同的函数引用。

设计取决于订阅是否真正依赖 `queryId`：如果 `queryId` 变化意味着订阅目标变化，就把它放入 Effect 依赖，每次变化时先用原回调引用清理旧订阅，再建立新订阅。

如果订阅事件始终相同，只是回调需要读取最新 `queryId`，则保持一次稳定订阅，用 ref 保存最新值，让稳定回调从 ref 中读取，避免每次状态变化都重新订阅。

`useCallback` 本身不能自动解决旧闭包：空依赖会继续读取旧值，把 `queryId` 放入依赖又会让回调变化并触发重新订阅。开发环境的 StrictMode 会执行一次“订阅—清理—再订阅”来暴露副作用问题；只要清理正确，就不会形成真实的重复订阅。

## 判断速记

`订阅目标变化 → Effect 依赖 queryId；订阅固定、只读最新值 → 稳定订阅 + ref。`

## 容易说错的地方

- 取消订阅必须使用与订阅时相同的函数引用。
- `useCallback` 只稳定引用，不会自动让闭包读取最新状态。
- StrictMode 的重复执行是开发期检查，不能通过关闭 StrictMode 掩盖清理问题。
