# 旧 HTML 引用的 hash chunk 被清理导致白屏，如何保证发布一致性？

> 主题：工程化 / 发布 | 频率：高

## 考点（面试官在考察什么）

- 构建原理、依赖边界、缓存发布与可验证收益。

## 核心答案（能直接讲出口的版本）

核心原则不是强制用户立即获取新 HTML，而是保证旧 HTML 在兼容期内仍能加载它引用的全部资源。

HTML 与 hash 资源采用不同缓存策略：HTML 使用短缓存或协商缓存，便于较快获取新版本；带 hash 的 JS、CSS 使用长期强缓存和 `immutable`，同一地址永不覆盖不同内容。

发布必须遵循“先资源、后 HTML”：先上传新版本所有 chunk，检查完整性和 CDN 可访问性，再灰度发布引用它们的新 HTML，最后才允许清理旧资源。旧 chunk 至少保留到覆盖 HTML 缓存、长期未刷新页面、灰度周期和回滚窗口，清理应结合版本清单与访问日志，而不是只保留最近一次构建。

动态 chunk 仍出现 404 时，不能只对同一个 URL 反复重试，因为确定已被删除的 hash 地址会持续返回 404。应用应在入口尽早监听 Vite 的 `vite:preloadError`；先区分临时网络波动和版本不一致，确认页面版本落后后保存输入草稿、当前会话等必要状态，再刷新一次以获取新版 HTML。使用 `sessionStorage` 记录刷新标记，避免资源服务持续异常时形成刷新死循环；仍失败则展示降级提示，并上报 HTML 版本、chunk 地址和错误信息。

项目当前可以确认已经实现的是 PC 对话组件预加载失败后的重试、监控和刷新提示，但尚未发现统一的 `vite:preloadError` 自动恢复机制。因此，面试时应明确区分：现有前端已经具备局部错误兜底；全局版本恢复和旧资源保留仍需要前端入口与发布平台共同补全，不能表述为线上已经完整落地。

回滚时只需把 HTML 或版本指针切回旧版本，因为旧 HTML 和对应 hash 资源仍然完整保留，可以快速恢复。

## 发布速记

`HTML 短缓存；hash 资源长期 immutable；先上传资源，再发布 HTML；旧版本延迟清理；ChunkLoadError 最多刷新一次。`

## 容易说错的地方

- hash 资源不应原地覆盖，否则长期缓存会返回错误内容。
- 新 HTML 发布成功不代表可以立即删除旧 chunk，旧页面仍可能长期存活。
- 自动刷新必须限制次数，否则持续资源故障会造成刷新死循环。
- 对确定已删除的同一 hash URL 重试无法解决问题，主要保障仍是发布顺序和旧资源保留。
