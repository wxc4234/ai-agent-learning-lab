# Hybrid WebView 如何在首屏速度、BaseData 新鲜度和失败降级之间做权衡？

> 主题：性能 / Hybrid 首屏 | 频率：高 | 关联项目：[ChatSearch AI](../../projects/chatsearch-hybrid.md)

## 考点（面试官在考察什么）

- 指标口径、瓶颈定位、优化方案与验证闭环。

## 核心答案（能直接讲出口的版本）

项目采用的是**页面初始化 + 发问前校验**两级屏障，而不是每次都强制等待在线 BaseData。

页面初始化时，`BaseDataController` 会同时读取缓存并发起在线请求。如果缓存未过期且 Native 实验参数 `nev` 一致，就先用缓存初始化 Store、快速展示首屏，在线结果只刷新缓存；缓存无效或未命中时，才等待在线 BaseData，失败后最多额外重试两次。全部失败则使用默认 Store 放行，推荐词降级到原有 guidewords 接口。

真正调用 `launchConversation` 前还会再次检查 token。缺少 token 时会复用首轮请求，必要时重新拉取 BaseData 并同步到 Store，避免页面虽然打开了，但实际发问缺少鉴权数据。

Native 兼容主要通过 `hybridInfo` 和离线包版本管理处理：命中 Hybrid 离线包才走新链路，老版本或没有该标记的客户端继续走原 Web 初始化；离线资源通过 manifest、MD5、有效期和版本号治理。

无有效缓存且网络请求长期挂起时，产品定义是阻断首屏，由客户端展示网络异常页并中断 BaseData 请求，而不是让缺少基础数据的用户进入一个基本不可用的页面。

这套方案的边界是缓存优先而非强一致：缓存命中后的在线结果只供下次使用，不会替换当前页面数据；前端请求本身没有独立超时，弱网阻断和异常页由客户端网络策略兜底。

## 流程速记

`有效缓存 → 首屏放行 + 后台刷新；无缓存 → 等在线数据；失败耗尽 → 默认 Store；发问缺 token → 再次门禁；长期挂起 → 客户端异常页拦截。`

## 容易说错的地方

- 不是所有场景都等待在线 BaseData，而是缓存优先的软屏障。
- 默认 Store 只保证页面可初始化，真正发问前仍需校验 token。
- 后台刷新只更新下一次使用的缓存，不保证当前页面拿到最新数据。
- 无缓存且请求长期挂起时不会直接放行，由客户端网络异常策略兜底。
