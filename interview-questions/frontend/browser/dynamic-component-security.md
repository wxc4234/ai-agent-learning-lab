# 动态组件如何限制脚本来源，并处理版本兼容、失败降级和灰度回滚？

> 主题：浏览器 / 安全 | 频率：中 | 关联项目：[ChatSearch AI](../../projects/chatsearch-overview.md)

## 考点（面试官在考察什么）

- 浏览器机制、生命周期、安全边界与异常场景。

## 核心答案（能直接讲出口的版本）

先说明项目现状：当前 `componentConfig.path` 会进入动态 `import()`，加载后按 `name` 从全局对象取组件并缓存；加载失败会丢弃当前 Block 并结束本包消费，避免队列阻塞。但现有代码中没有完整的域名白名单、版本校验和灰度回滚机制，不能说安全问题已经完全解决。

如果完善这套能力，服务端只能下发 `componentId + version`，不能直接指定任意 URL。前端通过受控组件清单映射到固定 CDN 地址，并校验 HTTPS、域名和文件 hash，再配合 CSP 限制脚本来源；真正不可信的第三方代码应运行在 sandbox iframe，而不是主页面上下文。

组件清单还要声明支持的平台、宿主 API 版本和最低客户端版本。加载前完成兼容性检查，组件只能通过稳定的 `AssistantAPI` 使用宿主能力；缓存键使用 `name@version`，避免同名不同版本互相污染。

加载过程需要超时和有限重试，失败后降级为文本或“不支持的卡片”，并继续触发 `render-finished`，不能阻塞整条 SSE 队列。同时上报组件名、版本、平台和失败阶段。

灰度由配置中心选择稳定版或实验版，同一轮会话固定组件版本。异常时通过 kill switch 关闭灰度，或把组件清单切回上一稳定版本；旧 hash 资源继续保留，从而无需重新发布主应用即可回滚。

## 设计原则

`服务端选择已登记组件，前端控制资源映射、兼容校验、执行边界、失败降级和版本回滚。`

## 事实边界

- 当前已有动态加载、按名称缓存和失败后放行队列。
- 白名单、hash 校验、版本契约、沙箱和配置回滚属于完善方案，不能表述为线上已全部实现。
- 仅使用动态 `import()` 不代表资源可信，核心是不能让服务端直接决定任意脚本地址。
