# AI 会话删除：事务、索引与缓存一致性各保证什么？

> 优先级：P0｜参考答案已整理、尚未模拟｜工作后端证据 U2/U3/U4 见[源码基线](../../projects/chatsearch-source-baseline.md)。

**项目边界：** 本文的工作代码证据来自 assistant-ui-go 的 MySQL 数据访问层，属于后端协作理解与源码复盘；Learning Lab 的 PostgreSQL 实践单独引用。源码存在不等于本人负责实现，个人职责和验证结果须分别提供证据。

## 是什么与为什么需要

数据库事务把多次数据库写组织为一个提交单位；索引控制查找与锁定范围的成本；缓存减少重复读取。三者职责不同，事务不会自动把 Redis、模型调用和文件操作一起回滚。

## 1. 删除会话与消息放一个事务，够了吗？

**参考答案：** U3 在 Repeatable Read 事务中删 topic 和 record，可以让这两次写同成同败。但生成任务若稍后重新插入消息，原事务已结束，仍可能出现孤立数据。需要写入方也遵守会话状态、锁顺序或版本约束；外部任务取消和 Redis 清理是额外协议。

**追问与答案：** Repeatable Read 就相当于串行执行吗？不是。隔离级别定义并发可见性，具体锁范围受语句、索引与访问方式影响。不能把普通快照 SELECT 当成 FOR UPDATE，也不能把 MySQL 的行为直接套到 PostgreSQL。官方说明见 [InnoDB 隔离级别](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)（核对：2026-10-22；不证明本地线上数据库版本）。

**验证计划：** 第二次删除失败回滚、并发追加、锁等待超时、死锁、提交成功但响应丢失；重试整个事务前先判断幂等与外部副作用，不能只重试失败 SQL。

## 2. 怎样从业务查询推导索引？

**参考答案：** U2 的等值条件是 uid/session_id/message_id，可以提出匹配这些查询的联合索引候选；会话内时间排序分页则要结合过滤、排序字段和稳定 ID 设计另一条访问路径。先检查现有 DDL、数据分布和 EXPLAIN，再决定顺序与覆盖字段。不能因为代码有 where 就宣布数据库有该索引。

**追问与答案：** 为什么不把 text 放进覆盖索引？正文很大，会增加写放大、空间与缓存压力；可先查小字段和 ID，再按需取正文。深 offset 分页会扫描被跳过的数据，稳定排序的 keyset 分页通常更适合增长中的历史列表，但需定义并发插入下的一致性。

**验证计划：** 多用户、单用户大量历史、相同时间戳、边界翻页、删除中翻页；看扫描行数与尾延迟，不只看小数据集耗时。

## 3. 数据库提交后删缓存为什么仍有竞态？

**参考答案：** 读请求可能先拿到旧 DB 值，写请求提交并失效缓存后，旧读再把旧值写回。Cache-aside 是性能策略，不天然强一致。可按业务选择版本化缓存、短 TTL、串行化更新或权威读；延迟双删依赖时序，不能作严格证明。

**追问与答案：** 如何可靠通知缓存失效或下游？可以把 outbox 记录和业务写入同事务提交，由后台投递并幂等消费。投递仍可能重复；Redis Stream 本身不把 MySQL 提交纳入同一事务。这里是增强设计，未声称工作项目已有 outbox。

## 4. 模型调用为什么通常放事务外？

**参考答案：** 模型等待长且可能失败，持有数据库连接和锁会放大竞争。先用短事务确认任务/权限与状态，事务外调用，返回后短事务按版本和当前权限提交结果。中途权限变更、删除或取消时必须重新判断；模型消耗和外部工具副作用不能靠数据库 rollback 撤销。
