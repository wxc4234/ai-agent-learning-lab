# Redis Stream 能保证 Agent 事件不重不漏吗？

> 优先级：P0｜参考答案已整理、尚未模拟｜来源：ChatSearch 后端源码复盘与官方命令语义。

## 是什么与为什么需要

Stream 是带 ID 的追加事件结构，可按位置回读。它适合把长任务生产者与短连接订阅者分开；连接恢复不必重新执行任务。它不是完整的任务状态机，也不是外部工具操作的事务日志。

## 核心回答

先定义四个不同确认点：Redis 接受写入、网关写出帧、客户端接受数据、业务副作用提交。任一确认点都不能自动代替其他三个。XREAD 读取大于给定 ID 的记录，业务游标若表示“下一条”，需转换成上一条起点；本项目的序号 ID 可以减一，不能推广为任意 Redis 时间戳 ID 的通用转换。

**当前协议边界：** 网关优先使用 `Last-Event-ID` Header；只有未提供时，才把 body 中表示“下一条”的 checkpoint 换算为 XREAD 起点。例如客户端收到 10 后传 11，未带该 Header 时从 `10-0` 之后读取。Redis 接受 XADD 并返回确认，与事件已满足所需的落盘、复制或故障切换保证不同；本轮没有核验部署中的持久化与复制配置。

官方定义见 [Redis XREAD](https://redis.io/docs/latest/commands/xread/)（核对：2026-10-22）。只使用其基本读取语义，不把最新文档新增参数当成本地部署能力。

## 1. XREAD 与消费者组如何选？

**参考答案：** 多个浏览器分别恢复自己的同一条任务流，需要各自游标读取；如果误用同一消费者组分摊，可能只有某个浏览器收到部分事件。后台任务队列希望不同 worker 分工时才考虑消费者组，并处理 pending、超时接管和幂等。广播订阅与工作分摊是不同问题。

**取舍：** 每个订阅者独立读会增加读取成本；可以限制订阅并发、读取批次和事件体积。不能为了节省读请求而破坏每个客户端的数据完整性。

## 2. 为什么唯一事件 ID 仍不等于幂等成功？

**参考答案：** 唯一性只阻止写第二份。同一事实重试需要返回已确认结果，而不是把所有重复都当成功；同 ID 不同内容是协议冲突。工程上要保存事件身份和内容摘要，写入成功但 ACK 丢失后能核对并补确认；对已经裁剪的事件，无法核对时应返回过期或未知，不能盲目 ACK。

**项目反例：** G3 对重复 ID 的 XADD 错误直接返回，不能把它描述成“重试无感成功”。Redis 返回成功也不能单独证明断电或主从切换后零丢失；复制与持久化策略要另外核对。

## 3. 为什么最大序号不是连续提交水位？

**参考答案：** 接收到 10 和 12，最大值为 12，但 11 可能尚未处理。若协议要求连续序号且从 13 恢复，会跳过缺口；确认水位只能推进到已连续提交的位置。若协议允许不可见事件或合法跳号，则先定义事件全集及跳号规则，不能强行把所有数字间隙判成丢失。

**取舍：** 要更强保证，需去重记录、有界乱序缓冲、缺口超时与权威快照恢复。只为连接重放提供 best-effort 游标成本低，但必须说明语义。

## 4. Redis 保留窗口如何影响容量与恢复？

**参考答案：** 条数裁剪限制历史长度，TTL 限制不再续期后的存活时间。近似裁剪不是精确内存上限，单条大事件仍会撑大内存。恢复请求早于首个保留事件时，应显式提示恢复窗口已过或从权威快照恢复，不能把剩余尾部当成完整回答。

**失败矩阵：** 写成功丢 ACK、重复 ID 异内容、消费者卡顿、坏包被跳过、流过期、恢复起点早于裁剪位置、客户端解析成功但业务消费失败。分别验证接受、回放与提交语义，不把“有 SSE 输出”作为唯一断言。
