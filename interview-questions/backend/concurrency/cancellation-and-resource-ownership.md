# Go 与 Python 的取消如何跨过流、线程和远程工具？

> 优先级：P0｜参考答案已整理、尚未模拟｜工作源码与学习实践分别标记。

2026-10-23 恢复原分类题目；工作事实对齐 2026-10-22 已核验的业务提交 `77d5befe`。本文保留 4 道通用并发题；具体工作源码、参数与失败边界统一见 [ChatSearch AI 全栈核对](../../projects/chatsearch-ai-fullstack-interview.md) Q3/Q4/Q6/Q16/Q17 与 K3，不把恢复文档写成重新运行测试。

## 是什么与为什么需要

取消是终止后续工作并收回资源的协作协议。AI 应用同时持有浏览器连接、模型连接、线程、数据库连接和外部工具；仅设置一个布尔值不能保证它们都停止。

## 1. Go Context 取消会自动结束 goroutine 吗？

**参考答案：** 不会。循环要检查 Done，阻塞 I/O 要支持 Context 或通过关闭拥有的连接来解除，退出路径还要关闭 pipe、释放 timer。发送者若永远等一个已离开的接收者，会泄漏 goroutine。清理应明确谁创建、谁关闭，防重复关闭或误伤共享资源。

**项目证据：** G1 把 HTTP Request Context 传入 pump，G2 有退出路径；这管理订阅生命周期，不等于取消独立 Agent。后者另走 G4 interrupt。见[源码基线](../../projects/chatsearch-source-baseline.md)。

**追问：** 缓冲 channel 能解决吗？只能推迟阻塞，不能替代取消与预算。Go 官方的[管道与取消](https://go.dev/blog/pipelines)解释了下游提前退出时上游阻塞的问题（核对：2026-10-22）。

## 2. Python async def 为什么仍然卡住整个服务？

**参考答案：** 同步网络、磁盘或 CPU 工作直接执行会占住事件循环；async 只是函数形式，不会把内部阻塞调用自动异步化。异步客户端适合网络等待，同步 I/O 可在线程执行，重 CPU 工作按实际运行时考虑进程或专用执行服务。线程池还需排队与并发预算。

**项目证据：** P1 用线程池运行后台任务；P4 的异步方法对特定 BOS I/O 走线程，避免直接阻塞 loop。不能把提交线程池当作持久任务调度或自动恢复。

**专用 loop 的边界：** 异步数据库连接等资源可能绑定创建它的 event loop；工作项目的控制面通过专用 loop 桥接，不能把执行链路概括为“所有代码都在一个后台线程池”。专用 loop 仍会被同步阻塞代码卡住；业务线程池、ADK executor 与子 Agent 池也不能合并成一个并发预算，具体见统一核对 Q4/Q17。

**追问：** 取消 await to_thread 会杀掉线程吗？不能假设。等待者可取消，但底层工作可能继续。不能立刻删除线程仍访问的目录、释放被认为已独占的资源或重复执行写操作。

## 3. TaskGroup、超时和 finally 应怎样配合？

**参考答案：** 把属于同一任务的子协程纳入明确生命周期，异常时取消并等待收尾。finally 中释放拥有的资源，捕获取消做清理后通常继续传播。吞掉 CancelledError 可能破坏结构化并发。超时应区分接入、读取、整任务和收尾预算，不能用每次重试都重置的局部超时冒充总预算。

Python [协程与任务](https://docs.python.org/3.12/library/asyncio-task.html)维护取消、TaskGroup、超时与 to_thread 的语言语义；核对时应使用项目 Python 版本，不照搬最新版本新增 API。

**shield 追问：** shield 可以阻止等待者的取消传播给被保护工作；它不让工作免于所有取消，也不保证副作用只发生一次。工作项目对部分控制面等待使用 shield，调用方超时后底层操作仍可能完成。需要继续托管在途工作、查询最终结果并按所有权清理，不能仅因超时就重试写操作；具体调用边界见统一核对 Q4。

**失败场景：** 工具线程写成功后协程超时；取消期间清理又失败；一个子协程失败而另一个仍向流写数据。记录已知副作用和未知结果，不能统一标为“没有执行”。

## 4. 怎么设计长任务停止协议？

**参考答案：** 先区分停止展示、断开订阅、请求取消和确认终态。对后台任务记录取消意图与执行归属；worker 在可中断边界检查，收尾后更新终态。对不可撤销写入，仅停止后续步骤并查询结果；若需要补偿，应设计独立补偿业务，而不是宣称取消等于回滚。

**工作实现与设计目标分开：** 已开始执行的工具遇到用户取消时，当前实现 detach 放弃等待，后台工具仍可继续；工具超时路径会向本地 task 发 cancel，但这不证明线程或远端操作已经终止。取消 API 返回成功也不能统一解释为所有资源已释放。上述都是原有机制的边界复核，具体证据与测试入口见统一核对 Q6/Q16；本轮没有执行这些测试。

**验证计划：** 下游提前关闭、缓冲耗尽、重复取消、子任务异常、同步 I/O 未返回、远程工具已提交但回执丢失。检查资源是否仍被使用，未知状态是否可核对，不只断言接口返回。
