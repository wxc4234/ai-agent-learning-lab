# 为什么密码要用专用哈希，验证失败应如何分类？

> 复习优先级：高 | 来源：第 4 周 Day 1 密码服务 | 状态：参考答案已整理、尚未模拟

## 参考答案与取舍

数据库保存密码哈希，不保存明文，也不使用可逆加密来支持找回原密码。专用密码哈希增加每次猜测的计算和内存成本；本项目使用 argon2-cffi 的 PasswordHasher，默认 Argon2id，并由库生成随机盐。相同密码的哈希可以不同，因此登录不能重新 hash 后比较字符串，而要用 verify 读取已保存哈希中的参数和盐进行验证。

盐不需要保密，编码字符串已包含它和算法参数。成本越高也越消耗服务端资源，部署前需要结合并发和内存预算测量；未来接入异步接口时不能直接在事件循环里执行昂贵同步运算，还需要限制并发和登录尝试。参数变化后，可在成功验证时检查是否需要重新哈希；本课尚未实现这一登录流程。

## 失败场景

- 密码不匹配：捕获 VerifyMismatchError，返回 False。
- 哈希损坏或其他验证故障：异常向上传播，由后续接口层安全处理；不能全部捕获为“密码错误”，也不能把底层细节直接返回客户端。
- 不对密码 strip 或转小写，不记录密码与完整哈希。本项目注册入口按用户选择拒绝所有 str.isspace 空白字符，长度 8～128；底层哈希服务仍原样处理输入，入口策略不应改变哈希函数语义。
- SecretStr 只提供常规展示与 JSON 序列化遮罩，取值哈希使用 get_secret_value()，不能哈希遮罩字符串。hide_input_in_errors 隐藏异常字符串中的输入，不等于原始 errors() 或请求日志安全；注册 HTTP 接口现已通过独立的错误响应与日志脱敏验收，见下方追问。
- 验证使用服务端保存的哈希，不接受客户端指定的哈希与计算参数。

## 追问：已有用户如何平滑增加密码登录？

保留 id、external_id 和会话归属，新增可空 username、password_hash，不为历史用户生成默认密码。使用命名 CHECK 约束要求两项同时为空或同时非空，唯一索引阻止重复登录名；注册入口还需要负责格式、大小写策略和密码规则，非空约束不等于密码强度或哈希有效性校验。存在用户名也不代表当前请求已经认证。

## 追问：注册仓储为什么只 flush、不 commit？

flush 在当前事务中执行 SQL、取得主键并触发唯一性检查，但不提交；上层才能把创建用户和后续相关写入统一提交或回滚。仓储内部 commit 会导致后续失败时已创建的账号无法一起撤销。用户名重复应由唯一约束兜底，不能以先查询替代约束，也不能返回已有用户当作注册成功。IntegrityError 应向上抛出并由事务边界回滚，不能在失败的 Session 中继续查询或将全部数据库错误当成重复用户名。UUID 业务标识由服务端生成，但不是认证凭证。

项目证据：test_registered_user_repository.py 共 7 条测试，包含第二次写入失败后整组回滚、重复注册不修改原账号，以及新 Session 读取提交结果。最初验收使用临时 SQLite；2026-09-13 已统一为独立 PostgreSQL 测试库，保留 7 条测试及独立 Session 提交验证，不声称已做 PostgreSQL 并发压测。重要程度：高；参考答案已整理、尚未模拟。

参考：[SQLAlchemy Session 与事务](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)。

## 追问：注册服务如何拥有事务并准确分类用户名冲突？

> 复习优先级：高 | 来源：第 4 周注册服务事务编排 | 状态：参考答案已整理、尚未模拟

服务接收无活动事务的 Session，统一执行哈希、仓储调用和 commit；flush 或 commit 失败都 rollback。拒绝已有事务是为了防止意外提交调用方的其他工作；若未来需要组合多项业务，应重新设计外层事务所有权，不能直接嵌套当前服务。

并发请求可能同时查询到用户名不存在，因此预查询不能替代唯一索引。SQLAlchemy 的 IntegrityError 包装了驱动异常：本项目核对 psycopg UniqueViolation、SQLSTATE 23505、users 表及 ix_users_username 索引后才转成 UsernameAlreadyExistsError；external_id 重复或凭证配对约束失败则回滚并原样传播。未知数据库来源也不猜测为用户名重复。

失败场景：使用 `raise UsernameAlreadyExistsError() from error` 时，即使业务错误文本安全，默认 traceback 仍会展示原始 SQL 异常与参数中的密码哈希。学习者改为 `from None` 后默认异常链展示被抑制，但原异常仍可存在于 `__context__`；日志系统收集局部变量或异常上下文仍可能泄露，因此后续 HTTP/日志边界必须独立脱敏。

项目证据：`apps/api/tests/test_registration_service.py` 共 10 条测试；2026-09-13 数据库测试统一到 PostgreSQL 后，后端默认 219 条通过，Ruff 通过。覆盖成功结果不含凭证、已有事务保护、哈希/提交失败回滚、真实用户名与其他约束分类、Session 恢复及默认回溯脱敏。统一 fixture 创建独立临时测试库与每例私有 schema，注册服务使用真实 commit；新增 2 条隔离用例验证不同物理连接间的提交/回滚可见性。测试结束自动清理，不污染开发业务数据，不声称已做并发压测。尚未接入注册 HTTP 接口。

## 追问：为什么业务错误安全，HTTP 响应或日志仍可能泄露密码？

> 复习优先级：高 | 来源：第 4 周注册 HTTP 接口与脱敏错误响应 | 状态：参考答案已整理、尚未模拟

请求校验在业务路由执行前发生，因此仅在路由函数内部捕获异常不够。注册接口用局部 APIRoute 包装原处理函数，在请求校验、业务执行和响应生成的边界返回白名单字段；不直接序列化 errors()、请求体或原始异常，也不改变已有聊天接口的错误协议。

HTTP 结果明确区分：201 创建账号、409 用户名冲突、422 无效输入、400 解析错误、500 内部故障。服务保留数据库错误分类，HTTP 层再提供安全通用错误；不能把所有故障当成用户名重复。错误输出采用固定 code/message，取舍是暂不提供逐字段详细原因，但避免输入、额外字段名或异常上下文被回显。

两种失败场景已实测：把 model_dump_json() 结果交给 JSONResponse 会重复编码，客户端收到字符串而不是对象，应该传 model_dump() 字典；logger.exception() 即使配固定文本，也会携带异常回溯，应该在当前边界只记录固定事件。最外层广义 Exception 捕获是有意的安全边界，使用带说明的局部 BLE001 豁免，不以记录完整异常来消除 lint 告警。

同步密码哈希与数据库调用放在普通 def 路由，由 FastAPI 在线程池执行；路由创建并关闭 Session，服务拥有事务。成功响应只包含 external_id 和 username，不包含哈希，也不设置登录 Cookie。

项目证据：`apps/api/tests/test_registration_api.py` 的 21 条测试覆盖成功持久化、重复用户名、无效输入/非法 JSON、未知数据库约束错误、恢复、日志与响应脱敏、Session 关闭、线程执行和 OpenAPI/既有路由行为。2026-09-13 后端 240 条通过，Ruff 通过，注册路由、响应模型和接口测试 Pyright 零错误、零警告；全部数据库测试使用独立 PostgreSQL，临时库已清理。课后归档不代表已经通过模拟面试。

## 追问：登录如何处理中文用户名与凭证错误？

> 复习优先级：高 | 来源：第 4 周登录凭证校验与中文用户名 | 状态：参考答案已整理、尚未模拟

注册规则约束新凭证，登录需要原样验证已存凭证。本项目注册仍要求密码 8～128 字符且无空白；登录接收 1～128 字符的 SecretStr，不 trim、不转小写，也不再次拒绝密码中的空白。未来修改注册策略不能未经分析阻止已有凭证登录。

用户名共用规范函数：首尾空白去除、ASCII 英文转小写，长度 3～64 个 Unicode 字符，允许统一汉字（含扩展及〇）、ASCII 字母/数字/下划线；不按 UTF-8 字节计数，不做 NFKC 全角转换。拒绝内部空白、不可见分隔符、标点和 emoji。数据库唯一索引负责并发兜底，支持中文不等于接受任意 Unicode 或消除视觉混淆。

未知用户、无凭证记录与错误密码返回同一业务错误；未知用户执行一次虚拟哈希验证后始终拒绝，即使虚拟验证返回 True。该策略减少明显计算路径差异，不保证请求恒定耗时，不能替代后续限流。损坏哈希、验证故障和数据库故障保留真实分类，不能全部伪装成密码错误。

服务不创建用户、不写会话、不 commit/rollback；查询使用 no_autoflush，避免刷新调用方未提交写入。AuthenticatedUser 只表示本次凭证校验通过，后续请求仍需要独立的会话认证机制。

项目证据：新增 test_login_request.py 51 条与 test_authentication_service.py 15 条测试，覆盖中英文规则、密码原样处理、成功/失败/故障分类、虚拟验证、事务保护及中文 HTTP 注册后凭证校验；2026-09-13 完整后端 306 条通过，Ruff 通过，本课核心与新测试 Pyright 零错误、零警告。尚未接入登录 HTTP 与 Cookie。
