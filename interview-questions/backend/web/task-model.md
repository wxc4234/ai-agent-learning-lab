# Task、Conversation 和 AgentRun 为什么分开建模？

复习优先级：高。参考答案已整理、尚未模拟。

Task 表达项目中的持续目标，Conversation 承载多轮交流，AgentRun 描述某一轮执行。一个 Workspace 有多个 Task，当前一个 Task 至多对应一个 Conversation，会话可有多个 Run。不能把最后一次 Run 的终态直接等同于任务整体完成。

## 旧数据与约束

Conversation.task_id 可空，让旧会话继续运行，不猜测归属或批量回填。PostgreSQL 普通唯一索引允许多个 NULL，但同一个非空 Task 标识只能关联一个会话。relationship 提供对象导航，数据库外键和唯一索引负责实际约束；back_populates 必须在正确的类上成对。

Task 的所有者沿 Workspace.user_id 查找；会话现有 user_id 仍保留。外键不能保证这两个所有者相同，未来创建服务必须先授权并在同一事务中创建 Task/Conversation。当前尚未实现此服务，不宣称关联约束已替代访问控制。

## 迁移故障与项目证据

create_all 可以创建新表，不能更新已有表，也不更新 Alembic 版本账本。开发库曾出现 Task 表已创建但会话列缺失的部分状态。只有核对版本、完整结构与表无数据并隔离演练后，才在一个事务中修复空表、执行真实迁移、比对目标结构并更新账本；不能直接 stamp 跳过缺失结构。

证据：test_task_model.py、test_task_migration.py；相关专项 41 passed，覆盖旧数据、NULL/唯一/外键、ORM 提交重读、真实升级回退及空表修复。开发库 f16a53d928bc，alembic check 无差异。Task 创建、恢复、删除及任务权限服务仍待实现。


## 如何避免只创建任务、没有创建会话的半成品？

创建服务拥有一个独立事务，先校验并锁定本人 Workspace，再创建 Task 与 Conversation，通过 ORM 关系安排插入顺序。会话 user_id 取自授权后的项目；flush 后复制普通结果，commit 成功才返回。会话插入、结果构造或提交前失败均整体 rollback；已有调用方事务必须在 try 外拒绝，避免误回滚别人的工作。事务内不等待模型、目录选择或外部调用。

证据：test_task_service.py 新增 25 条，相关回归共 46 passed。真实 PostgreSQL 验证 Task INSERT 已发生后，会话阶段 SQL 失败仍无残留；独立连接确认提交，过期配置开启时不重开事务，调用方未提交工作仍可自行提交。Task 创建服务已完成，HTTP/BFF/UI 仍待接入。重复调用创建不同任务，尚无请求幂等；模拟提交前异常不能证明提交成功后网络断开的结果可判定。复习优先级高，参考答案已整理、尚未模拟。


## Task 创建接口返回 500 为什么可能仍有两条已保存记录？

事务提交和 HTTP 成功响应不是同一个原子操作。服务提交后，响应构造或框架 response_model 校验仍可能失败。接口应返回固定 task_creation_uncertain 和安全提示，不说一定未创建；客户端在尚无幂等能力时不能自动重发。

证据：test_task_api.py 最终 33 条，分别注入提交后响应构造错误、结果字段错误和框架响应校验错误，验证身份/业务 Session 已关闭，500 不泄露原始信息，独立连接仍能查询到 Task 与 Conversation。此前“HTTP 待接入”的边界已完成；BFF/UI 和幂等恢复仍待实现。复习优先级高，参考答案已整理、尚未模拟。


Task 创建 BFF 补充证据：task-create-route.test.ts 59 条通过，校验请求项目与响应 workspace_id 一致、公开字段/错误白名单、来源与内部凭证、转发前后取消及正文阶段超时；没有自动重试。转发前取消可确认本次未提交，开始转发后无法据取消或错误断定事务未提交。BFF 已完成，上游为模拟，真实工作台集成与幂等恢复仍待接入。


## 禁用按钮能否保证创建请求幂等？

不能。ref 同步占位用于阻止 React 按钮更新前的连续提交；AbortController 和组件身份检查用于阻止旧项目响应修改当前 UI。这些都不能撤销已经提交的数据库事务。只有明确拒绝或明确未提交才恢复编辑；网络失败、未知响应或转发后超时应保留“结果未确认”，不能自动重发。成功后“创建另一任务”是新的用户操作。刷新或重新挂载会丢失当前表单的未知状态，服务端幂等和任务列表恢复仍需后续实现。

工作台集成证据：workspace-task.mjs 使用真实 BFF/API/隔离 PostgreSQL 验证创建、标题规范化和 Unicode 边界，并在上游返回 201 后主动丢弃响应，确认表单暂停提交、不重复发送。复习优先级高，参考答案已整理、尚未模拟。


## 首轮标题总结为什么不能放在数据库事务里等待？

模型响应延迟及失败不可控。先授权项目和任务、复制第一轮已保存的用户/助手消息，关闭读取事务，再请求模型。模型失败保留首条消息摘录；模型成功后重新授权并用旧标题作为更新条件，防止迟到结果覆盖新标题。标题调用与聊天回复解耦，既不让模型等待占用事务，也不使辅助功能失败遮盖已经完成的回答。

工作台已经支持笔形入口、首次发送创建 Task/Conversation、同一会话续聊及历史读取。创建响应丢失时可从任务列表找回已提交的空任务，仍未提供服务端创建幂等。证据：task_workspace.py、test_task_workspace.py、workspace-task.mjs；覆盖标题失败回退、重复总结跳过及迟到标题条件更新。参考答案已整理、尚未模拟，优先级高。本轮由教练按用户授权实现，不等于学习者独立掌握。


任务恢复补充证据：详情读取使用项目/任务公开标识直接查询，不依赖当前列表第一页；URL 标识仅定位资源，归属仍由服务端检查。test_task_detail.py 18 条覆盖分页外任务、项目与会话归属错配、公开字段和只读 SQL/Session 生命周期。详情 HTTP/BFF 与 URL 自动恢复已完成；历史运行摘要/时间线恢复仍待实现。归入已有资源归属与恢复主题，参考答案已整理、尚未模拟。


## 上游已经通过响应模型校验，BFF 为什么还要核对资源标识？

类型合法不代表资源匹配。详情 BFF 同时要求 workspace.external_id 和 task.workspace_id 等于 URL 中的 workspaceId，task.external_id 等于 taskId，并校验 conversation_id 格式。即使返回另一个合法任务也必须拒绝；会话真实归属由后端数据库授权保证，BFF 不能只凭公开标识格式证明所有权。白名单重建响应，避免新增内部字段被意外暴露。

取消和超时应覆盖 fetch 及正文读取；JSON 解析后再次检查 signal，防止迟到成功响应。当前共享读取代理统一返回脱敏 502，403/404/422 保留状态；如果将来要区分超时与用户取消，应统一设计协议。

证据：task-detail-route.test.ts 新增 58 条，Workspace 全量 383 条通过；实际 GET 路由配合模拟上游验证身份头隔离、资源错配、字段过滤、正文阶段取消/超时。未将模拟测试称为真实浏览器恢复验收。复习优先级高，参考答案已整理、尚未模拟。


## 刷新恢复任务时，为什么需要错误态、取消检查和稳定组件 key？

URL 只保存项目和任务的公开定位标识。详情验证后取得可信会话，再读取历史；详情失败不能回退为可发送草稿，否则用户可能误建新任务。列表只用于导航，不能作为恢复成功的前提，分页外项目/任务仍可直接定位。

AbortController 用于终止旧请求，await 之后还要检查取消状态；即使请求忽略 abort，也不能让迟到结果覆盖用户新选择。首次创建后写 URL 使用 replaceState，保留草稿 key，避免卸载正在发送首条消息的聊天组件。历史失败同样禁止发送。当前不建立任务切换的前进/后退历史，也不保存未发送草稿或恢复历史运行时间线。

证据：task-url.test.ts 新增 13 条；workspace-task.mjs 8 组真实 BFF/API/隔离 PostgreSQL 场景通过，包括复制链接、刷新后同会话续聊、分页外定位、详情失败与重试、旧详情和历史竞态。模型出口模拟。复习优先级高，参考答案已整理、尚未模拟。


## 删除任务时，为什么先锁会话再检查历史，而且不能只检查 running？

先查没有历史、再执行删除存在检查与使用之间的竞态。当前空任务删除事务按项目、任务、会话顺序授权加锁；会话 FOR UPDATE 与 PostgreSQL 子表 INSERT 检查外键所需的父行锁冲突。删除提交时等待中的 INSERT 外键失败，删除回滚时它可继续；若 INSERT 先取得锁并提交，删除等待后重新检查历史并拒绝。

Conversation 引用 Task，当前没有数据库级联删除，因此显式先删会话、再删任务，统一提交。任何中途错误整体回滚；已有调用方事务在 try 外拒绝，不擅自回滚。提交前复制普通结果，避免已删除或过期 ORM 对象再次触发查询。

取消接口会先写 aborted/error 再通知协程停止，因此终态不证明执行器已退出。本课拒绝任意状态的 Run，只接受空任务；数据库行锁也不能阻止另一条 get-or-create 链路在删除后按公开标识重新创建会话，开放删除接口前还要收紧聊天创建语义。

证据：test_task_deletion_service.py 新增 27 条，Task 领域 116 条通过，真实隔离 PostgreSQL；包含六个通过 pg_blocking_pids 观察锁竞争的并发用例。未开放删除接口，不宣称通用任务删除完成。复习优先级高，参考答案已整理、尚未模拟。


## 为什么删除保护还需要改变聊天入口的 get-or-create？

行锁保护当前事务，不能阻止未来请求按公开标识重新 INSERT。local 模式的会话只由 Task 创建事务生成，聊天必须拒绝不存在或无 Task 的会话，联合校验会话与项目归属；账号模式原有创建语义作为兼容分支保留。检查必须在缓存使用前，旧缓存不能成为授权依据。

创建 Run 时，在同一事务中锁定已授权会话后再写 Run/事件。删除先取得锁并提交时，Run 查询等待后得到不可访问；Run 先取得锁并提交时，删除等待后查到 Run 并拒绝。普通聊天的授权事务在模型等待前结束，不宣称它持锁覆盖整个模型调用，也不宣称该调用会被自动取消。

证据：test_task_conversation_boundary.py 新增 40 条，相关后端 189 条通过；真实 HTTP、缓存有无两种情况、SQL 无会话 INSERT、模型前锁释放和双向并发均覆盖。工作台首发/续聊/刷新恢复 1 组、本地免登录聊天/取消等 3 组浏览器通过。复习优先级高，参考答案已整理、尚未模拟。


## 为什么 DELETE 超时不能提示删除失败并自动重试？

优先级高；参考答案已整理、尚未模拟。

数据库提交与 HTTP 响应不是一个事务。后端提交后序列化失败，或 BFF 等待响应时断网，都可能出现记录已经删除但浏览器未收到成功的情况。只有转发前取消才能明确提示尚未提交；转发后取消、超时和未知响应统一使用 task_deletion_uncertain，要求刷新列表确认，不能声称回滚或自动重试。重复请求得到 404 也不能证明首次没有成功。

成功使用 204 空正文，BFF 不调用 json()；异常只接受状态与错误码匹配的白名单，返回自己维护的文案，防止上游 SQL、路径或凭证泄漏。409 task_has_history 是明确业务拒绝，应保留任务并提示目前只支持空任务。BFF 不复制上游响应头，凭证来自服务端配置。

取舍：结果不确定会增加一次读取，但保留事实边界；它不等于实现了请求幂等或支持有运行历史任务删除。UI 通过 Provider 保存操作状态，按当前项目与任务标识决定是否清除选择，避免迟到删除响应覆盖新的任务或草稿；查询详情失败保留未确认态。

证据：test_task_delete_api.py 42 条包含事务中 SQL 失败回滚、提交后异常及响应构造失败；task-delete-route.test.ts 43 条包含 204、状态错配、脱敏、请求/正文阶段取消和超时；相关后端 422 条、Workspace 439 条通过。BFF 由教练获明确授权实现，不记录为学习者独立实现。


### 前端如何确认删除结果，并避免异步操作覆盖用户的新选择？

复习优先级高；参考答案已整理、尚未模拟。

操作快照记录要删除的项目与任务；完成时读取最新 selectionRef，只清理仍指向目标的选择与 URL。如果用户已切换任务或进入新草稿，就只刷新列表并更新提示。URL 详情恢复尚未完成时，还要取消目标的旧恢复请求，防止已删除任务被迟到结果重新选中。

删除锁使用 ref 同步更新，拦截同一事件循环里的重复点击；状态放在工作台 Provider，不绑定任务行或侧栏的挂载生命周期。结果未确认时查询准确的任务详情，不从列表第一页的缺失推断删除成功。查询 200 只说明目前还存在，不证明先前 DELETE 已停止；保留未确认状态。404 只说明不存在或不可访问，不声称确定由本次删除完成。

取舍：目前未确认状态会阻止再次删除，且刷新页面会丢失客户端提示；后续可用服务端操作记录收敛最终状态。本课不引入幂等承诺。样式、图标与菜单不单独列为面试考点。工程证据见 apps/web/test/browser/task-delete.mjs 的真实 BFF/API、响应丢失和迟到结果场景。


加载体验补充：React key 应表达组件身份，不把刷新版本或选中状态混入项目 key。否则一次后台数据刷新会销毁列表、分页和展开状态，并重新显示初始 loading。仅稳定子组件 key 不够：三栏布局原本位于 keyed TaskChat 内部，父组件切换仍会销毁全部导航。当前将 Shell 提到 TaskChat 外，运行详情通过 Portal 渲染回固定右栏；项目使用稳定标识。revision 只驱动请求和重置分页，保留旧列表直到新数据返回。会话历史按任务隔离并重新读取，只延迟展示骨架 250ms，不跳过授权或历史加载，也不沿用另一任务的消息。失败仍阻止发送。


## 运行列表为什么先授权再查询，游标为什么取已返回的最后一条？

复习优先级高；参考答案已整理、尚未模拟。

Task 的 Run 通过已授权 Conversation 定位。先检查 Workspace 所有者、Task 所属项目和 Conversation 所有者，再查询 Run；否则“查询不到运行就返回空列表”会混淆不存在、不可访问和真实空任务。游标只限制 ID 范围，不扩大资源范围，也无需指向仍然存在的记录。

查询按 ID DESC 排序并取 limit + 1 条，多出的记录只用于判断下一页；next_cursor 必须取当前已返回页的最后一个 ID，再用 id < before 查询。误用探测行 ID 会导致漏项。新插入的较大 ID 不会挤进后续页，需刷新第一页；这种分页不提供跨请求快照，也不代表事务提交时间排序。

列表只选 run_id、status、started_at、finished_at，不访问事件关系；Session 关闭前构造响应，避免脱离会话后懒加载。未结束运行不伪造最终耗时，未知状态保留原值，数据错误不伪装成空列表。

证据：tests/tasks/test_task_run_query.py 44 条隔离 PostgreSQL 专项，覆盖游标记录已删除、新运行插入、跨会话隔离、无授权时不查询 Run、SQL 仅 SELECT 且不读取事件、禁止 commit、SQL 异常与无效持久化耗时的 Session 清理。

HTTP 边界补充：路径和查询解析错误、服务参数异常统一为安全 422；不存在或无权访问统一 404，真实空任务返回 200 空列表。数据库与响应序列化错误属于 500，不能误报输入错误或伪装空列表。成功和失败均 no-store；身份来自依赖，本地凭证留在服务端。证据：test_task_run_api.py 42 条真实 HTTP/隔离 PostgreSQL 测试，覆盖边界早于身份解析、默认与上限分页、归属拒绝、异常脱敏及响应结构失败。

BFF 补充：静态类型不能验证上游 JSON。运行概要必须匹配请求的 workspace/task，并检查记录严格倒序且小于请求游标；next_cursor 非空时应指向满页最后一条。重建字段避免内部数据泄漏，未知状态保留原值。取消信号要覆盖 fetch 和正文读取，并在 JSON 完成后再次检查，防止迟到成功。代价是增加边界校验，但不将数据契约错误伪装为空列表。证据：task-run-route.test.ts 79 条专项；参考答案已整理、尚未模拟。

运行历史 UI 的请求隔离：请求与已展示结果分开保存，刷新成功替换第一页，翻页成功追加；失败保留旧列表并重试原游标。任务标识作为组件 key 隔离状态，effect 清理同时 abort 与废弃旧回调；只取消网络而不限制回写仍可能出现迟到结果污染。加载骨架延迟 250ms，改善快请求闪烁，同时不改变真实请求状态。手动刷新展示最近一次查询快照，不把它当成实时运行订阅。复习优先级高，参考答案已整理、尚未模拟。

历史详情 BFF：持久化事件和实时流事件并非完全相同，取消写入的 RUN_ERROR 可能只有 reason，不能强行按 code/message 解析。已知流事件复用校验并重建公开 payload，持久化独有事件单独处理；未知事件保留信封且隐藏 payload。响应 run_id 必须匹配请求，事件 ID 严格递增，但不以时间戳代替排序依据。Run 所有权不等于当前 Task 关联证明。证据：run-detail-route.test.ts 新增 61 条，Workspace 全量 579 条通过；参考答案已整理、尚未模拟。

## 为什么应用启动不应使用 create_all 代替 Alembic？

复习优先级高；参考答案已整理、尚未模拟。

create_all 只创建缺失表，不把已有列/约束升级到新版本，也不记录迁移 revision；会形成新表已存在、旧表未升级、版本账本仍旧的部分结构。持久结构由显式 Alembic 迁移管理；应用 lifespan 只读检查数据库 current heads 与源码 heads 一致，失败则拒绝启动。检查关闭连接，不 commit，不自动 upgrade 或 stamp，避免多进程启动争抢 DDL。

版本一致仅证明账本一致，不能发现手动删列或错误 stamp 后的结构漂移；迁移测试仍需从空库执行真实迁移并验证结构。普通领域测试可以使用隔离 create_all 快速准备表，启动/迁移测试和浏览器启动则应使用真实迁移链。项目入口：app/database.py 的 check_database_ready；tests/migrations/test_database_readiness.py。


## 为什么创建幂等需要独立请求记录，删除 Task 后为什么还保留键？

复习优先级高；参考答案已整理、尚未模拟。

联合唯一约束以 user_id、workspace_id、request_key 为作用域，负责数据库级防重。请求键不能代替授权；服务端对规范化请求计算 SHA-256，同键不同内容应冲突。同键同内容返回已有任务身份，但不承诺可变标题与初次响应逐字一致。

Task 删除通过 ON DELETE SET NULL 保留请求记录。若连键一起删除，旧网络重试就可能再次创建任务。task_id 为空表示原结果已不可用，不能当成从未处理。当前不设置自动过期；回退迁移会丢失防重历史。

模型描述目标结构，Alembic 迁移把已有数据库升级到该结构。只改模型不会给旧库加表。新表无需猜测历史 Task 的请求键，也不回填。后续必须把 Task、Conversation 和请求记录放在同一事务提交；当前仅完成模型与迁移，尚无服务端幂等行为。外键只验证引用存在，服务仍须验证归属。

证据：apps/api/tests/migrations/test_task_creation_request_migration.py 的 17 条隔离 PostgreSQL 测试，覆盖真实升级/回退/再升级、旧数据保留、键与摘要格式、非空/外键/作用域唯一、ORM 持久化和真实删除服务提交后的键保留。并发请求的服务语义留给事务课验证。
